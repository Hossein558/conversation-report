# پرامپت آماده برای ایجنت‌های دیگر

هدف این سند: وقتی می‌خواهید ایجنت دیگری (Claude Code، Cursor، Gemini CLI، Codex، Windsurf، یا هر ابزار دیگری که خواندن فایل و اجرای دستور دارد) درباره کاری که در Antigravity انجام شده گزارش بدهد، فقط متن زیر را بدهید و `ConversationID` را عوض کنید.

## نسخه کوتاه

```text
روی این سیستم، مکالمه‌های Antigravity به‌صورت فایل متنی JSONL در این مسیر ذخیره می‌شوند:
~/.gemini/antigravity/brain/<ConversationID>/.system_generated/logs/transcript.jsonl
(روی ویندوز: C:\Users\<Username>\.gemini\antigravity\brain\<ConversationID>\.system_generated\logs\transcript.jsonl)

گزارش این ConversationID را برایم آماده کن:
<ConversationID>

کاری که باید بکنی:
1. فایل transcript.jsonl را بخوان. هر خط یک شیء JSON است.
2. خطوطی که "source":"USER_EXPLICIT" و "type":"USER_INPUT" دارند = درخواست‌های کاربر.
3. خطوطی که "source":"MODEL" و "type":"PLANNER_RESPONSE" دارند = پاسخ مدل. اگر فیلد "tool_calls" پر بود، ابزار اجراشده همان‌جاست و "content" معمولاً خالی است.
4. بعضی محتوای طولانی در transcript.jsonl با «<truncated N bytes>» کوتاه شده. اگر متن کامل خطا یا خروجی ابزار را لازم داشتی، همان خط را از transcript_full.jsonl در همان پوشه بخوان.
5. فایل خروجی هر مرحله زیر .system_generated/steps/<شماره>/output.txt است و خروجی تسک‌های پس‌زمینه زیر .system_generated/tasks/*.log.

خروجی نهایی که از تو می‌خواهم:
- خلاصه یک‌خطی موضوع مکالمه
- بازه زمانی، تعداد پیام کاربر، و اینکه آخرین کار در چه وضعیتی رها شده (تمام‌شده / نیمه‌کاره / منتظر تأیید)
- آخرین تسک: چه خواسته شد، چه اقداماتی انجام شد، نتیجه نهایی چه شد
- اگر خطا یا کار نیمه‌تمام مانده، صریح بنویس

مهم: این فایل‌ها فقط خواندنی هستند. هیچ چیزی را تغییر نده، هیچ سرویسی را ری‌استارت نکن، و هر فرضی که در فایل نیست از خودت اضافه نکن. اگر چیزی در فایل نبود، بگو «در لاگ ثبت نشده».
```

## نسخه کامل با بافت فنی

اگر می‌خواهید ایجنت دیگر دقیق‌تر کار کند، این نسخه را بدهید:

```text
تو باید یک مکالمه Google Antigravity را از روی فایل‌های محلی آن تحلیل کنی. هیچ دسترسی API وجود ندارد؛ همه چیز از دیسک خوانده می‌شود.

مسیر مکالمه:
~/.gemini/antigravity/brain/<ConversationID>/

فایل‌های مهم:
- .system_generated/logs/transcript.jsonl     → لاگ اصلی، هر خط یک رکورد JSON
- .system_generated/logs/transcript_full.jsonl → همان رکوردها با محتوای کامل‌تر
- .system_generated/steps/<شماره>/output.txt   → خروجی متنی هر مرحله
- .system_generated/tasks/task-*.log           → خروجی تسک‌های پس‌زمینه
- *.md در ریشه پوشه                          → مستندات و گزارش‌های تولیدشده

ساختار هر رکورد:
- step_index : شماره مرحله، صعودی ولی پیوسته نیست
- source     : یکی از MODEL یا USER_EXPLICIT یا SYSTEM یا SYSTEM_SDK
- type       : یکی از PLANNER_RESPONSE و GENERIC و USER_INPUT و SYSTEM_MESSAGE و ERROR_MESSAGE و …
- status     : وضعیت اجرا، معمولاً DONE
- created_at : زمان UTC
- content    : متن پیام، در رکوردهای ابزارمحور خالی است
- tool_calls : آرایه ابزارهای اجراشده
- error      : متن خطا در صورت وجود
- truncated_fields : فیلدهایی که محتوایشان بریده شده

قواعد تحلیل:
1. فقط رکوردهایی با source=USER_EXPLICIT و type=USER_INPUT حرف واقعی کاربر هستند.
2. رکوردهای MODEL با type=PLANNER_RESPONSE یا content دارند یا tool_calls، تقریباً هیچ‌وقت هر دو. برای دیدن کارهای اجرایی باید tool_calls را هم بخوانی.
3. فیلد thinking استدلال داخلی مدل است، نه پیام کاربر و نه نتیجه نهایی.
4. اگر رکوردی truncated_fields داشت یا در متن «<truncated ...>» دیدی، نسخه کامل همان خط را از transcript_full.jsonl بخوان.
5. شماره داخل نام فایل تسک با step_index یکی نیست. برای وصل کردن تسک به مرحله، رکورد GENERIC همان مرحله را بخوان که مسیر لاگ را داخل متن دارد.
6. اگر خطی JSON معتبر نبود، نادیده بگیر و ادامه بده؛ کل فایل را نامعتبر ندان.

خروجی نهایی:
1. موضوع مکالمه در یک خط
2. جدول خلاصه: بازه زمانی، تعداد پیام کاربر، تعداد رکورد، ابزارهای پرکاربرد
3. آخرین تسک: درخواست، اقدامات، نتیجه
4. وضعیت پایانی: تمام‌شده / نیمه‌کاره / منتظر تأیید کاربر / خطا
5. خطاها و کارهای نیمه‌تمام، صریح و بدون تعارف
6. اگر چیزی در لاگ نبود، بنویس «در لاگ ثبت نشده» و از خودت اضافه نکن

این فایل‌ها خواندنی هستند. چیزی را تغییر نده، دستوری اجرا نکن، و سرویسی را ری‌استارت نکن.
```

## نسخه بدون ایجنت: فقط اسکریپت

اگر می‌خواهید بدون درگیر کردن هیچ مدلی گزارش را ببینید:

```powershell
python src/conversation_report.py <ConversationID> --tools --errors
```

روی ویندوز با لانچر آماده:

```powershell
.\examples\check-conversation.cmd <ConversationID> --tools --errors
```

یا از ریشه مخزن:

```powershell
.\check-conversation.cmd <ConversationID> --tools --errors
```

## چه سؤالی از ایجنت بپرسیم

بسته به اینکه چه می‌خواهید، این‌ها پرسش‌های دقیق‌تری هستند که نتیجه بهتری می‌دهند:

| خواسته | پرامپت پیشنهادی |
| --- | --- |
| خلاصه کل کار | «این مکالمه را بخوان و در پنج خط بگو در مجموع چه کاری انجام شد و نتیجه چه شد.» |
| آخرین تسک | «آخرین تسک این مکالمه را پیدا کن و بگو چه خواسته شد، چه اقداماتی انجام شد، و نتیجه چه شد.» |
| کارهای نیمه‌تمام | «در این مکالمه چه کارهایی نیمه‌کاره رها شده یا منتظر تأیید مانده؟ با ذکر step_index.» |
| خطاها | «همه رکوردهایی که فیلد error دارند را فهرست کن و بگو هر خطا در چه مرحله‌ای و در چه زمینه‌ای رخ داد.» |
| فایل‌های تولیدشده | «در این مکالمه چه فایل‌هایی ساخته یا تغییر داده شد؟ مسیر دقیق هر کدام را بده.» |
| دستورهای اجراشده | «فهرست دستورهایی که با ابزار run_command اجرا شده، با شماره مرحله. بین دستورهای موفق و ناموفق تفکیک کن.» |
| دسترسی‌ها | «آیا در این مکالمه به سرور یا سرویس خاصی وصل شده؟ آدرس‌ها و پورت‌ها را فهرست کن.» |
| مقایسه دو مکالمه | «این دو مکالمه را مقایسه کن: چه کاری در هرکدام انجام شد و کدام ناتمام ماند.» |

## نکته‌های امنیتی هنگام دادن پرامپت

متن لاگ می‌تواند شامل این‌ها باشد:

- نام کاربری و رمز سرورها به‌صورت متن ساده
- توکن گیت‌هاب و کلیدهای API
- آدرس داخلی سرورها و پورت‌ها
- مسیر فایل‌های محرمانه

قبل از اینکه خروجی را جایی بفرستید یا در مخزن عمومی بگذارید، آن را بازبینی و پاک‌سازی کنید. اگر به ایجنت دیگری پرامپت می‌دهید که لاگ را بخواند، بدانید آن ایجنت همان اطلاعات را می‌بیند و ممکن است در گزارشش بازتاب دهد.
